## M3.1 Foundations (done, experiments pending)
- **Xcode project** `ios/Keepsake.xcodeproj` (generated by `ios/tools/make-xcodeproj.py`): app
  `com.harrisonfischberg.keepsake`, Share Extension `.share`, Widgets `.widgets`, App Group
  `group.com.harrisonfischberg.keepsake` on all three. Builds clean for the iOS 27 Simulator.
- **KeepsakeKit** (`ios/KeepsakeKit`, Swift package used by all three targets):
  - `RecordDatabase`: GRDB/SQLite (WAL) in the App Group; one table per shared store; exact Chrome JSON
    per record plus copied columns; `outbox` of changes; settings table; AI key in the Keychain.
  - `KeepsakeCore`: Chrome's `keepsake/src/shared` (bundled) running in JavaScriptCore over that
    database, so the iOS store *is* Chrome's store (D6).
  - `Library`: typed saves for screens (direct SQLite reads, live observation), writes through the store.
  - `Sealer`: X25519 / HKDF-SHA256 / AES-GCM with WebCrypto-made test vectors.
- **Tools** (`ios/tools`): `bundle-core.mjs` + `jsc-polyfills.js` (WHATWG URL etc.), `make-fixtures.mjs`
  (fixtures made by Chrome's own store), `sealer-vectors.mjs` (WebCrypto).

### Evidence
- `swift test` (macOS) and `xcodebuild test -scheme KeepsakeKit` (iOS 27 Simulator, iPhone 17):
  **10 tests in 5 suites pass**: Sealer vectors match WebCrypto; Chrome export imports to the same
  records Chrome itself produces; export → import is lossless; queryable columns and outbox; Chrome's
  import errors; golden `kindOf`/`normalizeUrl`/`classify` parity; secrets never in SQLite or exports;
  app + extension writing at once; 40 concurrent read-modify-writes with no lost write.
- `npm run test:ios-core`: URL polyfill = Node's URL on the whole corpus; bundle = ES modules; bundle up to date.
- `npm test` (Chrome): 293 pass, 0 fail (2 known-limitation todos, unchanged).
- Simulator, by hand: Safari → Share → **Keepsake** → "Saved" → the app's Library shows it, read from
  the shared App Group database (`item` row and 6 outbox rows confirmed with sqlite3).

### M3.3–M3.4 data layer (logic only; no screens yet)
`Library` now serves every list the screens need, decided by Chrome's own functions (`ios-bridge.js`
`views`): **Review** (`needsCollection`, not bought), **search** (`searchItems`: ranking and typo
correction), **Places by state then city** with **Places review** reasons (`placeState`,
`placeReviewReasons`), saves **by kind** and **by collection**, **goals with progress** (`goalProgress`)
and one-tap **check-ins with Undo**, **edits** that are protected as `userFields`, **moves** that teach
the categorizer, and **collections**.
- Evidence: expected answers made by Chrome's modules in Node (`Fixtures/views-expected.json`).
  `swift test` and the iOS 27 Simulator: **19 tests in 7 suites pass**. `npm test` 293/0. App builds.
- Chrome behaviours iOS now copies (worth knowing): "dutch ovn" is not typo-corrected (Chrome corrects
  only longer words); "lisbon" finds Café Azulejo only after correcting to "lisboa" (the region field).

### Found along the way
- Fixed: a bare page shared from Safari used to become a **Product** (no page data); it is now a Link,
  as in Chrome.
- Chrome's own rules classify the sample caption "Hip circles 2x10 … Deep squat hold 3x30s" as a
  **recipe**, not a workout (`recipeFromText` wins). That is current Chrome behaviour; worth a look in
  the extension, since iOS will match whatever Chrome decides.
- KeepsakeKit is linked statically into all three targets (three copies of the 300 KB bundle). Move it
  to a dynamic framework in M3.5's performance pass.

## M3.2 Vertical slice (done) · ⏸ review
Share Sheet → Library → open the save, in the chosen direction (D14), on the iOS 27 Simulator.
- **KeepsakeUI** (package target shared by the app and the Share Extension): Postcard palette (AA in
  light and dark), kind objects drawn from real saves (postcard, recipe card, ticket stub, book cover,
  tagged product, video frame, clipping, training card, link label) with states (Needs a collection,
  Finishing details, Bought/Done), press style, primary slab, chips, hold-to-stamp with rising haptics,
  scrims, the haptics map and named springs in code.
- **Library**: objects in two columns (one at accessibility sizes), kind chips and Review, search docked
  at the bottom (Chrome's ranking and typo correction), system Paste button to save a copied link,
  Import from Chrome, Undo toasts, Trash from the context menu, empty/loading/problem states.
- **Save detail**: opens from its card with a zoom; Place: postcard map with stamp, address rows,
  **Directions** (Chrome's `mapsLinks`, nothing looked up) and hold-to-stamp **Been**; Recipe: ingredient
  checklist, method, **Cooked**; others: Open/Watch/Read/Visit shop.
- **Share card**: saves first with Chrome's capture rules, then shows the save as its object, "Going to
  Recipes" on a slip you flick through Lifestyle views and collections (Chrome's `putItems` rules),
  Undo (removed outright, as Chrome), Add a note, auto-close after 2 s unless touched; duplicate and
  error states.

### Evidence

  destinations, put into a Lifestyle view then a collection, undo removes outright).
- UI tests (`KeepsakeUITests`, Simulator): **4 pass**: open a Place and stamp it Been; paste a YouTube
